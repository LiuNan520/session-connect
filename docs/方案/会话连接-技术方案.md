# 会话连接 技术方案

- PRD：`docs/prd/会话连接-PRD.md`（v8）
- 版本：v3 · 2026-10-21

## 改动概述

- 涉及项目：新项目 session-connect（空目录起步，只有 `assets/`、`docs/`、`AGENTS.md`）。
- 现状证据：本机 macOS 26.6.2、Node v25.7.0、npm 11.10.1；`osacompile`、`iconutil`、`codesign`、`ditto` 都在 `/usr/bin`；`/Applications` 当前用户可写（2026-10-21 实测）。
- 技术栈：
  - 单个 npm 包，TypeScript。
  - 后端：Fastify 5，跑在 Node ≥ 20；sharp 0.35 用于完整解码、校验图片。
  - 前端：React 19 + Vite 8 + @xyflow/react 12（React Flow）+ Zustand 5。
  - 测试：Vitest。
  - 应用图标：用 @resvg/resvg-js 从 SVG 渲染出 PNG，再用 `iconutil` 生成 .icns。
- 目录：

```
server/src/   本地服务：Fastify、数据读写、备份恢复、图标、导入导出、单实例锁
server/test/  后端测试
web/src/      前端（Vite 工程根目录是 web/）
shared/       前后端共用：类型、上限常量、按字计数函数
scripts/      build-app.mjs（生成应用）、app-launch.sh（应用启动脚本）、make-perf-fixture.mjs
assets/       内置图标、应用图标（已有）
dist/         构建产物：dist/web、dist/server
```

- 数据变更：没有数据库，数据存在 `~/.session-connect/`；测试时可以用环境变量 `SESSION_CONNECT_HOME` 换目录。

```
data.json            画布、偏好设置、图标元数据、导入记录（schemaVersion: 1）
icons/<id>.<ext>     上传的图标文件
backups/backup-YYYYMMDD-HHmmss.json
                     启动时的备份：data.json 全部内容，加上它引用的所有上传图标的字节（base64）；保留最近 10 份
logs/server.log      服务日志；启动时如果超过 5 MB，就改名为 server.log.1
instance.lock        单实例锁文件：持有者用系统文件锁（O_EXLOCK）打开并一直持有；文件永远不删除。
                     内容 { pid, port, mode: "app"|"dev", startedAt }，port 在选好端口前为 null
```

  data.json 的结构：

```
{ schemaVersion, prefs: { lastCanvasId, minimapVisible },
  canvases: [ { id, name, createdAt, revision, lastSaveId, viewport: {x,y,zoom},
                cards: [ { id, x, y, iconId, name, note, status } ],
                edges: [ { id, a, b, direction, label } ] } ],
  icons: [ { id, mime, hash, ext, createdAt } ],
  imports: [ { importId, canvasIds, iconsAdded, at, acked } ] }
```

  - `status`：`todo` / `doing` / `done` / `blocked`。
  - `direction`：`forward`（a→b）/ `backward`（a←b）/ `both`。
  - 画布顺序 = 数组顺序。
  - 内置图标 id 固定为 `claude-code` / `codex` / `deepseek` / `workbuddy`，不写进 `icons`。
  - 上传图标的 id 随机生成；`hash` 是 sha256，只用来去重。图标删掉后，同一张图再上传会得到新 id，所以已删除图标的卡片不会"复活"。
  - `lastSaveId` 和内容一起原子写入，服务重启后仍然能识别重复的保存请求。
  - `imports`：导入成功时，记录和导入的画布在同一次原子写入里一起写。前端拿到结果后会确认（ack）：
    - 没确认的记录永远不清理；
    - 已确认的只保留最近 20 条。

    因此，只要导入成功过，在前端确认之前一定查得到记录。

- 关键流程：
  1. 服务启动（应用和 `npm start` 共用）：先对 `instance.lock` 取系统文件锁（见后端任务"单实例"），取到锁之后才读数据、恢复、备份、选端口；选好端口后把端口写进锁文件。没取到锁，说明已经有实例，就返回它的地址。
  2. 点应用：applet 调用 `scripts/app-launch.sh`。脚本在后台启动 `node dist/server/index.js --mode app --handshake <临时文件>`，服务往握手文件里写一行结果：
     - `READY <url> <pid>`：新启动成功；
     - `RUNNING <url>`：已有实例；
     - `ERROR <原因>`：启动失败。

     脚本最多等 5 秒，按结果返回退出码（见后端任务）。applet 打开浏览器后常驻程序坞：每 3 秒检查一次 pid，进程没了就退出；点程序坞图标就再开一个标签页；退出时只 kill 自己启动的服务。
  3. 打开网页：`GET /api/state` 一次载入全部画布、图标和偏好设置。
  4. 编辑保存：
     - 前端改本地 store，按画布记"脏"标记；停手 800ms 后 `PUT content`，带上 `baseRevision` 和 `saveId`。
     - 服务加写锁，原子写入 data.json，revision + 1。
     - 同一张画布同时最多一个保存请求。请求结果未知（网络错误、超时）时，原样重试同一个请求（同 `baseRevision`、`saveId` 和内容），拿到明确结果后，才发送之后的新内容。
  5. 冲突：revision 对不上就返回 409，前端把这张画布设为只读；画布已删除就返回 404，前端弹"画布已被删除"。
  6. 切回标签页：先 `GET /api/canvases/meta` 比较，有变化时再 `GET /api/state`，按前端任务里的规则合并。

## 不做什么

- 不做 PRD"本期不做"和"二期"里的任何内容（真实会话关联、模板、搜索、分组、开机自启、复用已开标签页等）。
- 不做 WebSocket 或轮询来实时同步多个标签页，只在切回标签页时检查。
- 不开 CORS，不做登录。
- 不自动修改程序坞；不做 Windows、Linux 的应用。
- 不做英文界面，不引入 i18n 框架。
- 不对画布内容另设大小上限（PRD 第 14 节规定卡片数不设上限）。
- 不做分卷导出。

## 风险

- osacompile 生成的 applet 替换图标后签名会失效：替换后用 `codesign --force --deep -s -` 重新做 ad-hoc 签名。在 macOS 26 上要实测"双击能打开、程序坞显示圆点"；不行就停下告诉用户，不擅自换方案。
- 应用里记住的是生成时的 Node 绝对路径（`process.execPath`）。用 nvm 等工具升级 Node 后路径会失效，此时应用弹出"找不到 Node.js"，需要重新运行 `npm run app`。
- sharp 是原生依赖，要靠预编译包；首次 `npm install` 需要联网。装不上就停下告诉用户。
- 单实例依赖 macOS 的 `O_EXLOCK`（Node 没有导出这个常量，直接传数值 `0x20`）。本机已实测可用；如果以后的 Node 或 macOS 版本不再透传这个标志，单实例测试会失败，到时停下告诉用户。
- React Flow 在 200 张卡片、300 条连线下的性能，加上流动虚线动画：动画只用 CSS `stroke-dashoffset`，不靠 JS 逐帧算；以验收 A47 为准。
- DNS rebinding 和跨站请求：服务只监听 127.0.0.1；`Host` 不是 `127.0.0.1:<端口>` 或 `localhost:<端口>`、或者 `Origin` 存在但不同源的请求，都返回 403。
- 请求体技术上限 1 GB（Fastify `bodyLimit`）。超过 1 GB 的导出文件无法导入，已写进 PRD 的已知限制；按单个图标 1 MB 算，要大约 750 个图标才会碰到。

## 接口约定

通用规则：

- JSON 接口统一前缀 `/api`。错误统一返回 `{ code, message }`，前端按 `code` 显示 PRD 里的文案。
- 写盘失败返回 500 `WRITE_FAILED`，`reason` 为 `disk_full`（ENOSPC）/ `no_permission`（EACCES、EPERM）/ `other`，前端显示"未保存：{原因}，正在重试"。
- 网络错误、超时、没收到回复：前端一律按"连不上本地服务"处理；有副作用的请求按"结果未知"处理（见前端任务）。
- 文字长度按"字"（字素，用 `Intl.Segmenter` 计数）校验，前后端共用 `shared/` 的同一个函数和上限：画布名 1–30、卡片名 1–40、备注 0–60、连线文字 0–20；去首尾空格，换行替换为空格。
- 请求体上限：上传图标 1 MB，其他接口 1 GB（技术上限）。

| 接口 | 请求 | 返回 | 错误 |
| --- | --- | --- | --- |
| GET /api/health | — | `{ app: "session-connect", version, pid, port }` | — |
| GET /api/state | — | `{ schemaVersion, canvases, icons: [{id,builtin,mime,hash,url}], prefs, notice }`；`notice` 为 `null` 或 `{ kind: "restored"\|"reset", backupTime?, brokenPath }` | — |
| POST /api/notice/ack | — | 204，本次运行期间不再返回 notice | — |
| GET /api/canvases/meta | — | `[{ id, name, revision }]` | — |
| POST /api/canvases | `{ id, name }`，id 由前端生成 UUID | 201 新画布；id 已存在则返回 200 和已有画布（幂等） | 400 `INVALID_NAME` |
| PATCH /api/canvases/:id | `{ name }` | 200 `{ id, name }`；不改 revision | 400 `INVALID_NAME`；404 `CANVAS_NOT_FOUND` |
| DELETE /api/canvases/:id | — | 204；画布已不存在也返回 204 | — |
| PUT /api/canvases/:id/content | `{ baseRevision, saveId, cards, edges }` | 200 `{ revision }`。`baseRevision` 等于当前 revision 时写入，revision +1，并把 `lastSaveId` 设为本次的 `saveId`；如果 `baseRevision` 等于当前 revision − 1，且 `saveId` 等于持久化的 `lastSaveId`（上次已写入但回复丢了，包括中间服务重启过），直接返回当前 revision，不重复写 | 409 `REVISION_CONFLICT { revision }`；404 `CANVAS_NOT_FOUND`；400 `INVALID_CONTENT { detail }` |
| PUT /api/canvases/:id/viewport | `{ x, y, zoom }` | 204；不改 revision，后写的为准 | 404 `CANVAS_NOT_FOUND` |
| PUT /api/prefs | `{ lastCanvasId?, minimapVisible? }` | 204 | — |
| POST /api/icons | 请求体是原始文件字节，`Content-Type` 为文件的 MIME | 201 `Icon`；内容 hash 已存在则返回 200 和已有图标 | 415 `UNSUPPORTED_TYPE`；413 `TOO_LARGE`（> 1 MB）；422 `UNREADABLE`（见下面的图片校验） |
| DELETE /api/icons/:id | — | 204；已不存在也返回 204。不改任何画布，卡片遇到找不到的图标时由前端显示 Claude Code 图标 | 400 `BUILTIN_ICON` |
| GET /icons/:id | — | 图片字节；响应头带 `X-Content-Type-Options: nosniff`、`Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'` | 404 |
| GET /api/export | — | 作为附件下载，文件名 `会话连接-备份-YYYYMMDD-HHmm.json`（用 `filename*` 写 UTF-8 文件名）；内容 `{ format: "session-connect-export", formatVersion: 1, exportedAt, canvases, icons: [{ id, mime, hash, dataBase64 }] }`，`format` 必须是第一个字段（前端靠文件开头识别） | — |
| POST /api/import | 请求头 `X-Import-Id: <importId>`（前端生成 UUID）；请求体就是导出文件的内容 | 200 `{ canvasIds, iconsAdded }`。<br>处理过程：服务在开始读请求体之前，就把 importId 登记为"进行中"（只放在内存里）。画布和卡片、连线都生成新 id，追加到末尾；图标逐个按下面的规则校验，再按 hash 去重并重新映射 `iconId`。全部校验通过才写盘（全有或全无），导入的内容和 `imports` 记录（`acked: false`）在同一次原子写入里写。同一个 `importId` 再次提交，直接返回已记录的结果 | 400 `INVALID_FILE`（包括其中任何一个图标校验不通过）；400 `NEWER_VERSION`；400 `MISSING_IMPORT_ID`；413 `TOO_LARGE`（> 1 GB） |
| GET /api/imports/:importId | — | 200 `{ canvasIds, iconsAdded }`（已成功）；202 `IMPORT_IN_PROGRESS`（本进程还在处理） | 404 `IMPORT_NOT_FOUND`：没有记录，也没有在处理，说明这次导入没有提交（理由见下面的说明） |
| POST /api/imports/:importId/ack | — | 204，把记录标为已确认；记录不存在也返回 204（幂等） | — |

为什么 404 能确定"没有导入"：

- 导入的内容和记录在同一次原子写入里写，要么都在，要么都没有；
- 没确认的记录永远不清理；
- 正在处理的请求在读请求体之前就登记了"进行中"，查询会得到 202；
- 前端不给导入请求设超时，只有连接断开（服务退出）才进入"结果未知"，而且要等服务恢复后才查询。新进程里没有"进行中"的请求，所以查不到记录就说明没有提交。

图片校验（上传和导入都用这一套）：

- 声明的类型必须是 PNG、JPG、WebP 或 SVG 之一，否则返回 415。
- 位图用 sharp 完整解码（`failOn: 'warning'`，截断的图片也算失败）。
- SVG 先确认根元素是 `<svg`，再用 sharp（librsvg）完整解析并渲染一次。
- 任何一步失败都返回 422 `UNREADABLE`。

`INVALID_CONTENT` 会检查：

- 卡片、连线的 id 在本画布内不重复；
- 连线两端的卡片都存在，且不是同一张；
- 同一对卡片（不分先后）最多一条连线；
- 各个枚举值合法；
- 坐标是有限数；
- 文字长度在上限内。

## 后端任务

- [x] 工程骨架：`package.json` 脚本如下，tsconfig 分 server、web、shared，`.gitignore` 忽略 `dist/`、`node_modules/`、`.app-config`。
  - `dev`：vite 开发服务器 + tsx watch 运行服务，通过代理连起来；
  - `build`：vite build 输出 `dist/web`，tsc 输出 `dist/server`；
  - `start`：先 build，再运行 `node dist/server/index.js --mode dev --open`；
  - `app`：运行 `node scripts/build-app.mjs`；
  - `test`、`typecheck`。
- [x] `shared/`：类型定义、上限常量、`countChars`（字素计数）、`normalizeText`（去首尾空格、换行变空格）。
- [x] 数据存储：
  - data.json、备份、图标文件，写入一律用"同目录临时文件 + rename"保证原子性；进程内写锁，所有写串行执行。
  - 新增图标：先写图标文件，再写 data.json。删除图标：先改 data.json，再删文件。
  - 启动时删除 data.json 不再引用的孤儿图标文件（中途崩溃留下的）。
  - 首次启动没有 data.json 时，新建"我的画布"。
- [x] 单实例：
  - 用 macOS 的系统文件锁，由进程持有：
    - 取锁：`fs.openSync(instance.lock, O_RDWR | O_CREAT | O_EXLOCK | O_NONBLOCK)`。Node 没有导出 `O_EXLOCK` 常量，用 macOS 头文件里的数值 `0x20`。
    - 成功就是持有者，fd 一直开到进程结束。进程无论怎么退出（包括 kill -9），系统都会自动释放锁，所以不存在残留锁，也不需要回收。
    - 失败（EAGAIN）就是别的进程持有。
    - 2026-10-21 已在本机 Node v25.7.0 实测：第二个进程立即得到 EAGAIN；三个进程同时抢只有一个成功；持有者退出或被 kill -9 后，下一个进程立即拿到锁。
  - 锁文件永远不删除、不改名（否则等锁的进程和新建文件的进程会各锁一个 inode）。内容 `{ pid, port, mode, startedAt }` 由持有者通过同一个 fd 截断后原地改写；其他进程只用不带锁标志的只读方式读取。
  - 不是持有者时：每 200ms 重试一次取锁，同时读锁文件内容，用其中的 `port` 请求 `/api/health`。最多 5 秒内：
    - 先拿到锁：成为持有者，正常启动；
    - 先等到 health 通过：判定"已在运行"；
    - 两样都没等到：按启动失败处理（退出码 12，日志写明原因）。
  - 取到锁之后才读数据、恢复、备份；然后选端口（默认 4319，被占用时依次尝试 4320–4339），把端口写进锁文件。
  - 服务启动的子进程（如 `open <url>`）不能继承锁的 fd：libuv 打开文件默认带 O_CLOEXEC，要有测试覆盖。
  - 只支持 macOS：在其他系统上启动时直接报错退出（PRD v8"本期不做"已同步）。
  - 已在运行时：`--open` 就用 `open <url>` 打开浏览器；有 `--handshake` 就写 `RUNNING <url>`；然后以退出码 3 退出，终端提示"会话连接已在运行，已打开浏览器"。
- [x] 启动流程（持锁后执行）：
  - data.json 能读出来：先备份。备份内容是 data.json 全部内容，加上它引用的所有上传图标的字节；只保留最近 10 份。
  - 读不出（JSON 解析失败或结构校验失败）：
    - 把原文件改名为 `data-损坏-<时间>.json`；
    - 从新到旧找第一份能读的备份，用它重写 data.json 和 `icons/` 里的文件（保留原 id），生成 `restored` notice；
    - 都不能读就从空白开始，生成 `reset` notice；
    - 这种情况下本次不做备份。
  - `schemaVersion` 比当前版本低时按迁移函数升级（v1 暂时没有迁移）；比当前版本高时拒绝启动，日志写明原因。
- [x] 上表的全部接口，以及 Host、Origin 校验；静态托管 `dist/web`，内置图标随前端一起构建。
- [x] 日志：启动、端口、取锁结果、恢复或重置、写盘失败、退出原因（包括收到的信号，以及未捕获的异常：先写日志再退出）写进 `logs/server.log`；日志里不写卡片内容。
- [x] `scripts/app-launch.sh`：读项目里的 `.app-config`（`NODE=<绝对路径>`），在后台启动服务并读握手文件，按下面的退出码返回结果：

| 退出码 | 含义 | stdout |
| --- | --- | --- |
| 0 | 新启动成功 | `<url>\t<pid>` |
| 3 | 已经在运行 | `<url>` |
| 10 | 找不到 Node | — |
| 11 | 缺少 `dist/`（没构建） | — |
| 12 | 其他启动失败（等握手超过 5 秒也算） | 原因和日志路径 |

- [x] `scripts/build-app.mjs`（即 `npm run app`）：
  - 先检查应用是不是在运行：非阻塞地取一次锁。取到了就马上关闭 fd 释放锁，说明没有在运行；取不到，且锁文件内容里的 `mode` 是 `app`，就提示用户先退出，然后退出。（取锁的这一瞬间如果正好有服务在启动，它会在 5 秒的重试窗口里拿到锁，不受影响。）
  - 然后依次：`npm install` → `npm run build` → 写 `.app-config`。
  - 在临时目录里完整生成应用包：
    - 用 osacompile 编译一个常驻的 AppleScript applet，项目路径写死在脚本里；
    - applet 的处理：
      - `on run`：先检查项目目录在不在，再调用 `app-launch.sh`，按退出码弹 PRD 5.3 的对话框或者打开浏览器；
      - `on idle`：检查 pid；
      - `on reopen`：再开一个标签页；
      - `on quit`：只有服务是自己启动的才 kill。
    - 用 resvg 渲染出 iconset 里的各个尺寸，用 iconutil 生成 icns，替换图标，再改 `CFBundleName`、`CFBundleIdentifier`（`local.session-connect`），重新做 ad-hoc 签名，最后用 `codesign --verify` 检查。
  - 安装（整体替换，失败可回滚）：
    1. 用 ditto 把新包复制到 `/Applications/.会话连接.app.new`；失败就删掉这个半成品，旧应用不动。
    2. 把旧应用 rename 成 `/Applications/.会话连接.app.old`。

4. 图标异常的处理已由本轮 R1-1 修正：备份和导出跳过读不到、大小异常或 hash 不符的图标并记日志，画布、卡片、连线和其他有效图标继续保留；恢复时也逐个剔除坏图标，不再因此作废整份备份。仅备份副本过滤图标元数据，正常工作中的 data.json 不因备份或导出而改变；卡片保留原 iconId，由既有前端回退显示 Claude Code 图标。没有新增数据字段。

**和后端交付记录不一致的地方**

接口按后端实际代码对接，路径、字段、状态码都和后端交付记录、`docs/接口.md` 一致，没有发现后端缺接口或接口用不了。以下是前端实现上的取舍，以及和本方案"前端任务"文字有出入的地方：

1. 新建画布没收到回复：没有按方案"服务恢复后用同一个 id 重发一次"，改为服务恢复后重新拉一次 `GET /api/state`。原因：重发会在服务端真的没收到请求时，把用户已被告知"连不上…"的画布建出来，违背 PRD 12.2 / A37"这些操作不生效、什么都没改变"。重新拉取的效果是：服务端真的建了，画布出现在列表里；没建，什么都不变，同样不会重复。改名、删除没收到回复时也一样，在服务恢复后靠这次刷新核对。
2. "服务恢复"的判定（方案没规定）：任何请求连不上，页面就进入离线，之后每 5 秒请求一次 `GET /api/health`；任何请求成功即恢复。恢复时依次：刷新合并、核对待确认的导入、补发没成功的导入 ack。
3. 导入：点确认框的「导入」后先请求一次 `GET /api/health`，连不上就直接提示"连不上本地服务，请重新打开会话连接后再试"（A37），不进入"结果待确认"。health 通过之后，导入请求连接断开才进入"结果待确认"。
4. 超时：保存、改名等普通请求 30 秒超时，按"结果未知"处理；导入（按方案）和导出不设前端超时。
5. 保存队列的错误分类：409 只读；404 画布已删除；`WRITE_FAILED` 和其他 4xx（如 `INVALID_CONTENT`）按"明确没写入"处理，5 秒后用最新内容和新 `saveId` 重试；网络错误、超时、403、其他 5xx 按"结果未知"处理，5 秒后原样重发同一个请求。
6. 发送前规整内容：输入过程中卡片名可能暂时为空、或在输入法组字中超长，后端会返回 400。所以发给后端的内容一律去首尾空格并截断到上限；卡片名暂时为空时，发编辑前的名称。本地显示的内容不受影响，失焦时再按 PRD 处理（空名称恢复原名并提示）。
7. 导出：用 fetch 拿到文件内容，再触发浏览器下载（这样能区分"连不上"），文件名取响应头里的 `filename*`。导出前只等"可以保存"的画布存完；已被拒（409）或已删除的画布不阻止导出（PRD 说这些改动本来就会丢）。当前画布只读时「导出全部数据」不可用（PRD 第 18 节）。
8. 回退图标用 `/icons/claude-code`，不用静态的 `/icons/claude-code.svg`：后端的 `GET /icons/:id` 路由会先匹配到 `/icons/*.svg`，静态文件取不到。
